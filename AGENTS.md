# OpenSourceCAM development

Read docs/ARCHITECTURE.md and docs/FEATURE_PARITY.md before changing shared behavior.
Use the existing checkout; preserve user edits and fetch current main before publishing.

- Keep model/planning/postprocessing rules in Rust. Browser code handles presentation,
  file selection, downloads and browser persistence. Do not duplicate CAM formulas in JS.
- Shared application operations belong in src/commands.rs. Keep the browser adapter thin.
  Calculation commands live there; browser editing/history belongs in src/session.rs.
  Native desktop history migration is pending; do not claim it is already unified.
- Return errors for invalid inputs. Keep existing size/resource limits and export preflight.
  Do not weaken checks to make a project generate or export.
- Never claim a disabled, planned or desktop-only feature works in the browser.
  Update the parity document when availability changes.
- For behavior fixes add a regression test that exercises the failure. Keep changes scoped.
- Browser PWA and shop hosting are the active development targets. Native desktop
  development and automatic packaging are paused; retain native source and manual build tools.
- Run python3 scripts/check.py web for browser/shared engine changes. For shared Rust
  changes also run Clippy/tests with --no-default-features, as routine CI does.
  Use native/all checks when explicitly changing native code or resuming native work.
  Report skipped/unavailable tests separately from passes. CAD bundle tests need the runtime.
- No credentials, personal identity, private machining files or local machine paths in commits.
  Preserve dependency attribution/license files. Check commit identity before publishing.
- Website files are generated by scripts/package-web.py. Do not hand-edit deployed output.
  Tested main builds publish to gh-pages. Do not create a second deployment mechanism.
- Do not add paid services, controller connections or external project uploads incidentally.
